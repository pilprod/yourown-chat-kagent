# Обязательные проверки интеграции

Это профиль `kap-managed-single-run-v0`, а не полная upstream API v2
conformance. Наличие API, CRD или unit-теста само по себе не считается
доказательством работы в общей системе K8s Agents Platform.

| ID | Статус на `5229184` | Сценарий и критерий успеха |
|---|---|---|
| KAP-C001 | Частично | Повтор создания для одного доверенного субъекта, namespace и `request_id` возвращает тот же AgentInstance; параллельные дубли и конфликт Harness/Template отклоняются |
| KAP-C002 | Заблокирован | После разрыва клиентского соединения конечное состояние и артефакты сохраняются независимо от контекста запроса; Get/List/Subscribe совпадают, события не теряются, исходный запрос не проигрывается автоматически |
| KAP-C003 | Частично | Отмена, повторная отмена, потеря ответа, перезапуск и гонка с завершением приводят к одному сохранённому конечному состоянию; изменяющий данные инструмент после отмены не продолжает работу |
| KAP-C004 | Не реализован | Корневая Task в состоянии `input-required` переживает перезапуск и продолжается в той же Task только после подтверждённого ввода; зафиксированный шлюз пока отвергает `Message.TaskID` |
| KAP-C005 | Заблокирован | Нельзя подделать `x-user-id`, tenant или operator metadata; субъект A не может управлять жизненным циклом, вызывать send/get/list/subscribe/cancel и читать историю или артефакты субъекта B |
| KAP-C006 | Не доказан | Вызов инструмента имеет стабильные ключ идемпотентности и хеш запроса; автоматического повтора нет, неоднозначный результат становится `UNKNOWN` до сверки с provider или отдельного решения |
| KAP-C007 | Заблокирован | Среда исполнения достигает MCP только через Tool Gateway; блокируются прямой URL, перенаправление, альтернативный порт и адрес из plugin `mcp.json` |
| KAP-C008 | Не доказан | Повтор безопасен в трёх окнах: AgentInstance создан без ответа, сообщение принято без Task ID у клиента, конечная Task сохранена до фиксации workflow |
| KAP-C009 | Частично | Suspend/resume/delete отклоняют активную работу, переживают перезапуск каждого шага подготовки, отсутствие Actor даёт `FAILED`, потерянных ресурсов нет |
| KAP-C010 | Заблокирован | Прерывание между вызовом инструмента и его результатом не повреждает историю; следующее обращение работает либо получает явную отметку восстановления или ошибки |
| KAP-C011 | Заблокирован | Доверенная identity сохраняется по пути канал → Temporal → адаптер → kagent → Tool Gateway; прямой обход через controller или runtime недоступен |
| KAP-C012 | Заблокирован | Учётные данные изолированы по пользователям, не попадают в контракт среды исполнения и обновляются после ротации без пересоздания AgentInstance |
| KAP-C013 | Не доказан | Agent Card и статус Harness публикуют только возможности, реально прошедшие набор проверок; отключённые continuation, shares и checkpoint не рекламируются |

Exactly-once нельзя обещать для внешней системы, если provider не поддерживает
idempotency или reconciliation. В таком случае правильный результат —
`UNKNOWN` без автоматического повторения, а не ложный успех или скрытый повтор.

## Известные upstream-связи

- [#2447](https://github.com/kagent-dev/kagent/issues/2447) — запись конечного
  состояния может быть отменена вместе с клиентским контекстом;
- [#2464](https://github.com/kagent-dev/kagent/issues/2464) и
  [#2465](https://github.com/kagent-dev/kagent/issues/2465) — HITL continuation;
- [#1270](https://github.com/kagent-dev/kagent/issues/1270) — authentication и
  multi-user boundary;
- [#2277](https://github.com/kagent-dev/kagent/issues/2277) — повреждение history
  после прерванного обращения к инструменту;
- [#2326](https://github.com/kagent-dev/kagent/issues/2326),
  [#2404](https://github.com/kagent-dev/kagent/issues/2404) и
  [#2181](https://github.com/kagent-dev/kagent/issues/2181) — per-user MCP OAuth,
  ротация и смешение identity в кэше.

Исправление в `5229184` освобождает активный слот Task при следующей отправке
или сверке, но не предотвращает потерю конечной записи. Поэтому KAP-C002
остаётся заблокированным до проверки системы как «чёрного ящика».

## Последовательность доказательства

1. Локальные unit-тесты используют зафиксированный `a2a-go/v2` и проверяют
   только типы протокола, идентификаторы, routing metadata и fail-closed
   конфигурацию.
2. Регрессионный тест в fork воспроизводит конкретный дефект и сопровождает
   минимальное исправление, сначала предлагаемое в upstream.
3. Controller-only delta preview lane собирает controller и неизменённый UI
   companion из exact source commit, блокирует API, CRD, migration, runtime и
   UI source drift, сохраняет SBOM/provenance и допускает в testbed только оба
   digest без HIGH/CRITICAL находок.
4. Общий testbed проверяет настоящий поток AgentInstance/A2A вместе с
   Temporal-адаптером, доверенной identity и сетевой границей Tool Gateway.
5. Только после успешной проверки совместимости отдельно проектируется stable
   qualification; preview не получает production promotion автоматически.

На этом этапе ни один удалённый testbed-прогон и ни один preview release не
заявлен как выполненный.
